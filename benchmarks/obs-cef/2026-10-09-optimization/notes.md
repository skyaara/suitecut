# Diagnostic notes and evidence boundaries

This is a separate optimization run. The original 90-trial archive and report remain the before-change evidence. The original archive is immutable; its reproducible runtime log files in the working tree were reused when restarting OBS and are not claimed to have the original archive's hash.

The original source was already C++ for CEF rendering, I420 conversion, frame serialization and audio capture; FFmpeg/libvpx/x264 do encoding in native code. JavaScript schedules capture consumers, forwards pixels, implements session lifetimes and controls publishing. A rewrite of the entire application would not itself repair encoder settings, timestamp semantics or lifetime ownership.

The first recorder diagnostic supplied approximately 606 pixel buffers in a ten-second capture, but 600 writes reused the same Buffer. The encoded marker changed only six times. Encoder backpressure made the constant-rate time-slot catch-up loop keep encoding stale pixels. Native raw Matroska input now carries actual capture timestamps, retaining at most the current and newest pending frames and an end-of-recording held frame. The output is variable-rate VP9 WebM; there is no synthetic claim of 60 unique frames per second.

A separate real source-reuse experiment recorded 25 clips on the same live CEF source. Forced GC after each completed recording isolated retained buffers. Before the lifecycle fix, post-GC array-buffer memory rose by one 960x540 I420 frame (777,600 bytes) per cycle. Source failure/close Promise observers held completed session contexts. Removable source observers and explicit frame-reference cleanup fix that growth. Forced GC is used only for this retention experiment and after soak cleanup, not during the continuous soak.

Process RSS sums can double-count shared CEF pages. The soak additionally records PSS and USS every ten seconds. Samples identify processes and roles, CPU as percent of one core, thread counts and file-descriptor counts. Native recording and streaming share a CEF source in the soak, so this is a concurrency stress/memory check and is not compared to serial OBS FPS results.

Raw Node CPU profiles, event-loop measurements and FFmpeg blocking counts do not establish JavaScript as the principal limiter. The original recording used substantially less than one Node core while stale-buffer encoding and drain stalls dominated. The stream experiment improves after limiting x264 and filter thread counts on the four-core-quota host. The rejected frame-thread variant and diagnostic H.264 recorder substitution are retained; neither is a production change.

The timed comparison uses three trials per pipeline and case, ten-second motion workloads, alternating order, serial execution, one-second page warmup and half-second encoder warmup. Cases: 720p60 canvas, 1080p60 canvas, 4K30 canvas, 4K60 wheel scroll. Marker transitions are divided by the actual timestamped media interval from the first active marker to the container end. Longest marker holds use elapsed presentation timestamps. Nominal container FPS is metadata and is not the denominator. Stream-only checks use received media duration.

OBS here has no browser-source plugin; it captures a sandboxed external Chromium browser using XSHM/Xvfb. SuiteCut uses sandboxed CEF offscreen capture. Browser revisions, capture paths, codecs, audio tracks and encoder settings differ. The software-rendered, four-core-quota result is an available-production-pipeline comparison, not an intrinsic language or codec ranking. Hardware/GPU paths, other platforms, arbitrary sites and remote network reliability are outside this test.

No finite run proves freedom from all leaks or indefinitely stable memory. The continuous test and repeated lifecycle experiment support claims only for the observed browser workloads, build and durations. CEF and FFmpeg are external native dependencies; process memory plateaus do not constitute a complete allocation audit of their internals.

Page-wrapper lifetime observation is bounded with one weakly cached source signal per live browser, instead of adding two pending observers for every wrapper. The 200-recording test and paired snapshots use that lifetime-fix build. The final build also corrects capture clock upper bounds and accepts bounded future audio presentation timestamps. Exact source hashes are retained alongside each run.

The first complete thirty-minute run had stable managed memory but failed received-audio validation at the midpoint. Recorded Opus remained audible. Received AAC packets and decoded PCM show actual silence; lossless remuxing did not repair it. That failed run remains under `soak-before-audio-window-fix`, including relocation metadata and diagnostics. Do not use it as a passing audio or long-run correctness result.

The second long run corrected clock/future-audio bounds and had audible midpoint AAC, but its live receiver midpoint window had approximately 219 ms p95 absolute A/V error and finalized recording had approximately 217 ms (unchanged fixture threshold: 200 ms). It remains under `soak-before-capture-stamp-fix`. Its first eleven minutes include short verification, minute 16–17 includes a live receiver decode, and later minutes overlap a two-minute diagnostic pilot and verification. It is neither a passing long run nor a clean performance comparison.

The video encoder previously associated selected pixels with the scheduled output slot rather than actual capture time. Frames retained across asynchronous processing or missing/evicted capture slots must retain the timestamp of those pixels. The corrected build passes that association through encoded output. The overlapping short pilot failed the flash-count/sync criteria; all six decoded windows remain saved. One parallel unit test timed out under the same encoder contention; all 66 tests pass when run serially with a 30-second harness timeout. A separate serial pilot checks the build; the final thirty-minute recording/streaming run executes without additional source-reuse, comparison, unit, build or live-decode tasks. Subsequent OBS comparisons and feature checks execute serially.

A deliberately interrupted pilot and failed startup when the old display/audio runtime ended remain diagnostic evidence. The runtime and long-run drivers use detached process groups.

Native audio permits up to 250 ms of future presentation time. The previous live buffer discarded data over 100 ms ahead, while the one-way native handshake could overestimate the clock offset. Capture receipt now tightens that clock upper bound, and the buffer accepts at most 500 ms of future audio while preserving bounded history. New source-offset counters and beginning/middle/end decoded audio checks measure the result; the guard mismatch alone does not prove the cause of every prior silent sample.

The first serial capture-stamp pilot used 120 ms pulses. All six A/V windows had p95 below 84 ms, but the last receiver window had only four flashes and failed the five-match requirement. The final serial pilot and long run use 250 ms flash/tone pulses (still one-second periods), making the signal observable during sparse video capture. Neither the minimum five matches nor the p95 limit of 200 ms is weakened. This fixture adjustment does not change production source or the OBS comparison fixture. Failed pilots remain separately saved.

OBS's saved default x264 settings use automatic threading, whereas SuiteCut explicitly limits its encoders to four threads and its FFmpeg filter graph to one. After the clean long run and default serial comparisons, a separate OBS runtime repeats all 24 alternating recording trials and three stream trials per backend with only OBS `x264opts=threads=4` changed. This tests the encoder-thread policy concern on the four-core quota host; codecs, capture paths and browser revisions still differ. The original isolated OBS encoder settings are restored after this control run.

The clean 1080p60 simultaneous-output attempt completed thirty minutes but failed received start-window synchronization at 203.33 ms (strict limit: 200 ms). Complete audio analysis additionally found 15.20 s recorded silence and 19.86 s received silence near minute 24. At that point Node had a 16.18 s event-loop gap, the independent Python sampler had gaps of 4.18/11.92/2.88 seconds, and CPU progress across native processes fell sharply. This does not isolate JavaScript as the cause. Observer/host causality remains unproven. The failed run is retained as `soak-60fps-private-sampler-stall`; its full decoded PCM, RMS traces, all six A/V windows, private-memory samples and independent sampler gaps remain evidence.

The final long verification targets supported 1080p30 and disables repeated private-memory walks. It samples CPU/RSS/threads/descriptors and records sampler execution cost. Both the frame target and monitor differ; passing cannot establish that private-memory sampling alone caused the earlier stall. The previous thirty-minute stress data still supplies PSS/USS observations. Final role-RSS totals are explicitly RSS and can double-count shared pages. No whole-application C++ rewrite was justified by these measurements.

The 1080p30/lightweight-monitor attempt also completed the thirty-minute active workload but failed received start-window sync (298.33 ms, with one outlying periodic nearest-onset match). Full-file audio found a 13.18 s silent interval in both the recording and stream. This falsifies any claim that disabling private-memory walks and lowering the frame target solved long media reliability on this host. The recording's three sampled sync windows passed. Its complete failed result and all six windows remain saved. Repeated short OBS comparisons proceed after completed workload analysis; they cannot turn a failed long run into a pass.

The final 30 fps run has an observed maximum Node event-loop gap of 7.34 seconds and an independent sampler gap of 9.60 seconds. `soak/process-sampler-gaps.json` preserves before/after process observations. Source audio offset counters continue until cleanup; the `audioPackets` scalar is copied before stop, so the final offset count can exceed it. Neither a sampler correlation nor native processes making little progress establishes the cause.

The thread-control profile snapshot already contains four-thread options on disk, whereas the still-running original OBS log has no custom thread setting. The restarted control runtime explicitly logs `threads = 4`. Use active encoder logs to distinguish the runtimes; the before/after JSON alone does not establish a change in active settings. Captured on-disk settings are restored.

Final verification found a duplicate control-runtime launch. Its Xvfb/Pulse bindings failed, the failed coordinator raised KeyError Xvfb, wrapper/recorded PIDs conflicted, and the claimed profile restoration did not match. Those 24 readable/moving recordings and 24 short stream checks remain diagnostic under `-runtime-collision` suffixes and are excluded from the final controlled ranking. The full directory relocation map and preserved original paths are in `checks/thread-control-runtime-collision.json`. The control series is repeated under an exclusive coordinator lock, with runtime cleanup registered even on startup failure and encoder-profile restoration verified after shutdown. The default runtime comparison and long-run evidence are unchanged.
